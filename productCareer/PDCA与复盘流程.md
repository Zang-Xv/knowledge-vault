# PDCA流程

PDCA 是一种经典的 持续改进管理方法论，最早来自质量管理领域，现在被广泛用于 企业管理、技术流程、生产管理、DevOps、项目管理 等场景。

PDCA 代表四个循环阶段：

| 缩写      | 含义        | 作用                             |
| --------- | ----------- | -------------------------------- |
| P – Plan  | 计划        | 发现问题，分析原因，制定改进方案 |
| D – Do    | 执行        | 按计划实施方案                   |
| C – Check | 检查        | 评估执行效果，验证是否达到目标   |
| A – Act   | 处理 / 改进 | 根据结果标准化成功经验或修正问题 |

它的核心思想是：
持续循环改进（Continuous Improvement）

循环形式如下：

Plan → Do → Check → Act
      ↑               ↓
      └────持续循环────┘

每完成一轮，就会进入下一轮更高水平的改进。

### 怎么进行无责复盘

无责复盘（Blameless Postmortem）关键其实不是“大家心里不要责怪”，而是 通过结构和语言设计，让复盘天然不会指向个人。

下面是工程团队常见的几个核心做法。

#### 一、复盘的对象必须是“系统”，而不是“人”

无责复盘的第一原则：

问题来自系统设计，而不是个人错误。

在复杂系统里：

错误是不可避免的
关键是 为什么系统允许一个错误变成事故了以及应该如何防御

#### 二、避免 “为什么你” 的问题

很多复盘失败，是因为语言无意中变成审讯。

例如：

❌ 为什么你没有测试？
❌ 为什么你没发现？
❌ 为什么你当时这么做？

这些句式天然会触发防御。

更好的问法是：

✔ 当时的上下文是什么？
✔ 当时有哪些信息是可见的？
✔ 哪一步本来应该拦截这个问题？
✔ 我们可以增加什么保护？

这样讨论就会变成 系统分析。

关于个人错误和责任边界, 有一个工程管理的经典概念"just culture(公正文化)"

##### 公正文化

公正文化认为：

不是所有错误都应该被同样对待。

它把错误行为分成三类：

| 类型              | 含义     | 处理方式        |
| ----------------- | -------- | --------------- |
| Human Error       | 无意失误 | 改进系统        |
| At-Risk Behavior  | 风险行为 | 教育 / 调整激励 |
| Reckless Behavior | 鲁莽行为 | 个人责任        |

这三类行为的处理方式完全不同。

#### 三、用“时间线复盘”，避免价值判断

成熟团队通常采用 事件时间线（timeline）。

结构通常是：

14:02 发布版本
14:05 监控报警
14:07 用户反馈
14:10 回滚
14:15 服务恢复

只描述：

发生了什么

谁做了什么动作

不做评价。

评价留在后面。

这样可以避免复盘一开始就进入情绪。

##### 如何发起这样一场"时间线复盘"

时间线复盘的重点不是主持人“知道答案”，而是 帮助团队把事实拼起来。

常见方法：

提前收集信息
事故相关人员简单写下：
自己做了什么
时间点
看到的信号
主持人负责结构，而不是结论

主持人的工作是把信息串起来，比如：

14:02 发布版本
14:05 监控报警
14:07 用户反馈
14:10 回滚

然后针对关键节点问：

当时谁最先看到报警？
为什么报警没有更早触发？
回滚为什么花了3分钟？

主持人更多是 整理和引导，而不是提供技术判断。

#### 四、复盘的输出必须是“系统改进”

如果复盘最后只是：

写报告
做总结

团队会觉得 复盘没有意义。

真正的复盘必须产出：

可执行改进

例如：

增加自动化测试
增加发布审批
增加监控指标
增加回滚脚本
更新文档

但同时这也会带来流程负担和膨胀, 这在一定程度上是不可避免的，但成熟团队会控制一个原则：

改进措施必须和风险等级匹配。

常见做法是类似“成本—风险权衡”：

| 事故影响 | 改进方式         |
| -------- | ---------------- |
| 小问题   | 文档补充、提醒   |
| 中等问题 | 增加自动化检查   |
| 严重问题 | 流程或架构级改进 |

如果每次事故都增加复杂流程，就会产生所谓的 “流程膨胀（process creep）”。
很多团队会定期反过来审查：

这些流程是否真的降低了风险？

所以改进并不是一味增加规则，而是 寻找最小成本的防护点。
