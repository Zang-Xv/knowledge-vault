# 数据回流

在业务中往往能够听到领导强调数据回流，这是个有些神秘的名词
数据回流到底是什么？

我对数据的理解在于，收集数据可以让业务完成回环反馈
强调的是一个“闭环”：
业务系统产生数据 → 数据被采集/清洗/汇总 → 回到数据平台或模型系统 → 用于分析、决策、优化 → 再反过来影响业务系统
所以只要搞定数据怎么来，到哪里去，怎么指导生产就行了
但总是隐约感觉还不太对，这个概念和数据回流的差别到底有多大呢？

## 回流和数据展示

我在知乎搜索了一下，得到：
概念：数据回流就是指将数据仓库的计算结果表中的数据导入生产系统数据库的对应表的过程。
大概是：数仓算出结果 → 找到生产系统里承接这个结果的表 → 按字段关系写进去，让业务系统能查到并使用。

数据展示
或者说是报表，看板功能，是将数据展示出来供人查看
但是计算、分析、决策需要另外完成

但回流则是把分析固化下来，直接在前端中展示经过分析处理的数据结果
或者说将原始数据或经过初步处理的数据重新引入到数据处理的流程中，以便进行更深入的分析和挖掘。
可以直接提醒并辅助进行决策
类似于将手工查看报表和BI之后得出策略方向的过程自动化一部分

## 数据库和数据仓库

生产数据库，也常叫：

- 业务库
- 线上库
- OLTP 数据库（联机事务处理 On-Line Transaction Processing）
- 生产库
- 主库/从库

要求：稳定、准确、低延迟、事务一致。

数据仓库，也常叫：

- 数仓
- 数据平台
- OLAP 数据库（联机分析处理 On-Line Analytical Processing）
- 分析库
- 离线数仓 / 实时数仓

要求：适合大规模查询、聚合、关联、历史分析。

现在的理解是：生产库的数据经过处理和清洗之后，才能输入到数据仓库里面
用ETL数据同步工具 + ODS/DWD/DWS/ADS 分层一层层处理

为什么要这样区分成为两个数据存储系统？
避免报表查询拖慢业务系统
生产库表结构适合业务操作，不一定适合分析

## 模型的数据回流

把模型在线使用过程中产生的输入、输出、人工修正、用户反馈、业务结果等数据收集回来，用于评估、优化、再训练模型。

模型判断错了 → 人工改了 → 错误样本被记录 → 后续用于优化模型
